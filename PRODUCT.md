# Product

## Platform

web

## Users

The primary user is a solo self-hoster: one technical person running mcpelevator on their own machine (Docker, Unraid, a homelab box) for their own MCP clients and devices. They already know what an MCP server is and usually have a launch command (`npx -y …`, `uvx …`, a docker image, a remote URL) in hand. They want each server reachable from clients that can't spawn local processes, Claude mobile in particular, and then mostly want to stop thinking about it.

Multi-user support (role-bound control tokens, per-user server ownership) exists but is secondary. A shared small-team instance is a supported case, not the one design decisions start from.

## Product Purpose

mcpelevator turns stdio MCP servers, along with already-remote MCP URLs and REST APIs described by OpenAPI documents, into authenticated Streamable-HTTP endpoints (`/s/<slug>/mcp`, or `/g/<name>/mcp` for a group). It runs and supervises each server, puts auth in front of it, and hands back a URL to paste into a client.

It has succeeded when the user can add a server, press start, copy the URL, connect from any device, and then trust it to stay up: supervised, restarted when it should be, idled when unused, with failures that explain themselves.

## Positioning

One self-hosted container on one port does all of it. The protocol bridging comes from FastMCP. mcpelevator is the control plane around it: process supervision through desired-state reconciliation, bearer and control-plane auth with Host/Origin enforcement, sealed secrets, a catalog of public MCP directories, groups, usage counters, an optional REST/OpenAPI surface per server, and a built-in control MCP so an agent can manage the instance itself. The core loop is "add, start, copy URL"; nothing beyond the container needs to be installed.

## Operating Context

- Deployment: Docker or Docker Compose (bound to loopback by default), an Unraid Community Applications template, or local dev. Sometimes it sits behind a reverse proxy or Cloudflare Access.
- Clients: Claude mobile/desktop/web, other Streamable-HTTP MCP clients, stdio-only clients through `mcp-remote`, plus curl, automations and GPT Actions through the REST mirror.
- Typical work: install from the catalog or a GitHub repo, paste a launch spec or a `{"mcpServers": …}` config, watch startup and logs, set secrets and tokens, hide or relabel tools, group servers, check usage, restart or retry a failed server.
- Agents use the same control plane through the built-in `mcpelevator` control MCP. Its tool descriptions are the only docs an agent ever sees.
- Usage pattern: intense during setup and debugging, otherwise occasional check-ins, including from a phone.

## Capabilities and Constraints

- Runners: `npx`, `uvx`, `command` (local runners), `docker` (opt-in, root-equivalent), `remote`, `openapi`, `graphql`, and the built-in `mcpelevator` control server.
- Server lifecycle states: running, starting, unhealthy, failed, stopped, idle (quiesced, wakes on request). Operator actions write desired state and the supervisor converges, so the UI reflects eventual state and does not issue direct process commands.
- Per-server: secret env and headers (write-only, shown as `<hidden>`), disabled tools, tool overrides, health checks, idle timeout, a source repository with a post-clone script, upstream OAuth, and REST/OpenAPI exposure.
- Control plane: access tokens scoped to `all`, one server, or `group:<name>`; users and roles; runtime settings; usage buckets (hourly per-tool counts, never arguments); catalog mirror; debug mode.
- Frontend: SvelteKit (Svelte 5 runes), static SPA with no SSR, served by the backend. Tailwind v4, LayerChart for charts.
- Terminology lives in `CONTEXT.md` (Server, Server activation, Server restart, Idle quiescence, Wake-on-request, Disabled tool, Tool override, Usage bucket…). UI copy should use those terms and avoid the listed alternatives.
- Security posture is authorization, not isolation: local runners execute as the process user. The UI must never suggest stronger isolation than that.

## Product Principles

1. **Add, start, copy URL.** The shortest path from a launch command to a working endpoint comes first. Everything else is reachable but never in the way.
2. **State is truth, shown honestly.** The UI reports desired versus observed state as the supervisor sees it, including idle, starting and failed, and every failure explains itself (last error, logs).
3. **Secure by default, caveats stated.** Write-only secrets and Host/Origin checks are always on. Control-plane auth defaults to `auto`: it requires a token once the instance is reachable off-host, and a loopback-only install accepts `/api` calls without one. The UI is explicit about what is and isn't protected.
4. **One control plane, any operator.** Whatever a person can do in the UI, an agent can do through the control MCP, with the same permissions and the same vocabulary.
5. **Calm when it works.** Most visits are quick check-ins. A healthy instance should read as quiet, and attention goes to whatever needs action.

## Accessibility & Inclusion

Target WCAG 2.2 AA: every control reachable and operable by keyboard, AA contrast for text and state indicators, state never shown by color alone (the lifecycle pills carry labels), respect for `prefers-reduced-motion`, and usable at phone width, since check-ins often happen on a phone.

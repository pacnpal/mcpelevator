Self-hosted, MIT licensed

Every MCP server you use. One place you own.

Stop running the same servers in every client and pasting the same API keys into five config files. mcpelevator runs all of your MCP servers in one self-hosted container, gives each one an authenticated URL, and lets roles, ownership and scoped tokens decide who can see, run and call what.

    Consolidate

    Your MCP setup is scattered. Pull it into one place.

    Every client keeps its own list of servers, its own copies of your keys, and its own way of launching them. Your phone can't launch anything at all. mcpelevator runs each server once, on hardware you control, and every client points at it.

    Access control

    Own it. Decide who gets what.

    Admins and members, per-user server ownership, and tokens scoped to one server, one group or everything. The rules live in one place in the code, so the UI, the API and an agent on the control MCP all get the same answer. Pick a person to see what they get.

    Servers

    Can do

      Tokens they can mint

      Roles and ownership

      Every server has an owner. Admins see and manage all of them. Members see only their own, and anything else returns 404, the same as a server that doesn't exist, so ids and slugs don't leak. Settings, groups and users are admin-only. An admin can hand a server to someone else without restarting it.

      Scoped tokens

      allevery bearer-protected server and group
      srv_…one server and nothing else
      group:teamthe /g/team/mcp bundle only
      controlthe control plane, as a login

      Identity without passwords

      • Login tokens. An admin mints one per user. It's shown once and only its hash is stored.
      • Cloudflare Access. The signed-in email maps to the user with that name, for OAuth-only clients like claude.ai.
      • Break-glass. MCPE_ADMIN_TOKEN always works, and the last admin can't be demoted or deleted.

      How it works

      One container, one port, a bridge per server.

      FastMCP does the protocol bridging. mcpelevator is the control plane around it: it supervises the processes, checks every request, and gives you a UI and an API to run it all from.

      01 Add

      Paste a launch command, a Docker image, a remote URL, an OpenAPI document or a GraphQL endpoint. Or import a whole mcpServers config, or install from the public MCP registry.

      02 Start

      Each server gets its own bridge process on a loopback port, with a real PID and its own log, so one crash doesn't take the rest down. SQLite holds what you asked for and the supervisor keeps converging to it, even across restarts.

      03 Copy

      The copy menu has a ready config for Claude Code, Claude Desktop, Claude web and mobile, Codex, ChatGPT, Gemini CLI, VS Code and plain mcpServers. Paste it and you're connected.

      Runners

      If it can become MCP tools, it can live here.

      A runner is just how a server gets started. All of them end up behind the same auth, supervision, ownership and copy menu.

      npx

      npm packages

      Node and npx ship in the image, so npx -y … servers run with no extra setup.

      uvx

      PyPI packages

      Python servers run through uv. A native build toolchain is in the image for packages that compile on install.

      command

      Anything you can type

      Any command line, including a server cloned from a GitHub repo and built from its own checkout.

      docker

      Container images

      Runs images with a locked-down docker run. Off by default, since Docker daemon access is root-equivalent.

      remote

      Already-remote MCP

      Proxies an existing HTTP or SSE MCP URL behind your own auth. Sign in to the upstream with headers or OAuth.

      openapi

      REST APIs

      Point it at an OpenAPI document, pasted or by URL, and every operation becomes a tool.

      graphql

      GraphQL APIs

      Each query and mutation field becomes a tool, validated against the schema before it's sent.

      mcpelevator

      It manages itself, too

      A built-in control server lets an agent do anything the UI can, with the caller's own permissions.

      Features

      Everything you'd end up building yourself.

      Getting a stdio server onto HTTP is the easy part. Keeping a dozen of them up, locked down, shared and debuggable is where the time goes.

      Supervision that explains itself

      Desired state in SQLite, converged by a supervisor, Kubernetes-style. Failed starts retry with backoff, and the card shows the last error and the log tail, so you're not guessing.

      RunningStartingUnhealthyFailedIdleStopped
      starting attempt 1/5 failed: setup exited with code 100
      starting retrying in 2s, then 4s, 8s, 16s
      running bridge on 127.0.0.1:41021 · 14 tools

      Idle shutdown, wake on request

      Servers nobody has called in a while get stopped. The next request wakes one and waits until it's ready, so the client just sees a slower first call.

      runningidlewakerunning

      Groups

      Bundle servers behind one URL. Tools get the member's slug as a prefix, and connected clients hear about membership changes right away.

      /g/team/mcp
      ├ github_search_issues
      ├ linear_create_issue
      └ memory_create_entities

      Tool policy

      Hide a tool, rename it, rewrite its description, or add aliases so old names keep working. It applies to MCP, REST and groups at once.

      delete_repository hidden
      search_issues → find_bugs
      alias search_issues still works

      A REST mirror

      Turn on REST and every tool is also a plain POST, with a generated openapi.json for curl, automations and GPT Actions.

      POST /s/time/rest/get_current_time
      GET /s/time/rest/openapi.json

      Write-only secrets

      Mark an env var or header as secret and it's encrypted at rest and reads <hidden> from then on. It's decrypted in one place, right before launch.

      GITHUB_TOKEN = <hidden>
      Authorization = <hidden>
      LOG_LEVEL = info

      Usage per tool

      Hourly call counts for every server and tool, and never the arguments. You find out which tools get used and which ones nobody touches.

      Agents

      Your agent can run it too, by your rules.

      Every install ships a built-in mcpelevator server with 43 tools. An agent can install servers, read logs, build groups and mint tokens, the same things you'd click through in the UI.

      • Same permissions as the caller. Each tool is a call to the same /api route the UI uses, carrying the caller's token. A member's agent sees the member's servers and nothing more.
      • Two switches. One for the whole instance and one per user, so you can take it away from one person.
      • Kept out of bundles. A "*" group never picks up the admin tools. It joins a group only when you name it.

      Security

      Locked down by default, upfront about the limits.

      Two independent layers check every request, and both have to pass. Then the role checks decide what the caller may do.

      Host/Origin allowlist

      Always on, against DNS rebinding. A loopback Host only counts when the connection really comes from loopback, so an exposed box can't be fooled by Host: localhost.

      Per-server auth

      none, bearer or oauth for each server, with a default for the rest. Tokens are stored as SHA-256 hashes.

      Control plane locks itself

      In the default auto mode, /api requires a login as soon as the config says the box is reachable off-host.

      Secrets stay secret

      Encrypted at rest, masked in every API response, and turned into install prompts in .mcpb exports.

      Docker is opt-in

      When on, containers run with --cap-drop ALL, no-new-privileges, PID and memory limits, and secrets passed by name.

      Groups are deliberate

      None exist by default. A bearer group only opens to a token scoped to it, or an all token.

      Authorization, not isolation. Local runners execute as the mcpelevator process user and can read its data directory, including other servers' settings. Roles split up who manages what. They don't sandbox servers from each other. Only give the local-runner permission to people you'd trust with the machine.

      Quickstart

      From zero to a setup you control.

      Steps 1 to 3 get you a working server on a URL. Steps 4 to 6 add the groups, tokens and users that make it yours.

      Docker and ComposeOr Unraid, or Python with uv plus Node for a source install.
      Nothing else on the hostNode, npx, Python, uv and a native build toolchain ship in the image.
      A URL, if you want it off-hostA reverse proxy or tunnel with HTTPS. Loopback works out of the box.
      1. 1

        Run it

        Pick how you want to host it. Data persists in a volume, and the port is published to loopback only until you say otherwise.

        $ git clone https://github.com/pacnpal/mcpelevator
$ cd mcpelevator
$ docker compose up -d --build
# open http://127.0.0.1:8080

        The Docker runner is off by default. The compose file shows both ways to give it a daemon, including an isolated Docker-in-Docker sidecar.

        Install mcpelevator from Community Applications. The template lives in pacnpal/unraid-templates and comes set up for a headless box: host networking so the LAN gate sees real client IPs, appdata at /mnt/user/appdata/mcpelevator, and LAN access on from the first boot.

        Full walkthrough: docs/unraid.md.

        # control plane on http://127.0.0.1:8080
$ cd backend && uv sync && uv run uvicorn app.main:app --reload

# UI with hot reload on http://localhost:5173
$ cd frontend && npm install && npm run dev
      2. 2

        Sign in

        On loopback, the UI and /api are open with no token, so you can set things up right away. Once the instance is reachable off-host (a public base URL, expose mode or LAN access), the control plane requires a login, and the first boot prints an admin token once.

        $ docker compose logs mcpelevator | grep -A4 "auth is ON"

        Save it, since only its hash is kept. If you lose it, MCPE_ADMIN_TOKEN gets you back in. The API examples below assume export T=<your admin token>.

      3. 3

        Add your servers

        Three ways in. All of them work from the UI too.

        $ curl -X POST http://127.0.0.1:8080/api/servers \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' -d '{
  "name": "Memory", "runner": "npx", "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-memory"],
  "enabled": true
}'

        It's live at /s/memory/mcp as soon as it reports Running.

        $ curl -X POST http://127.0.0.1:8080/api/servers/import \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' \
    -d @claude_desktop_config.json

        Takes a standard {"mcpServers": {…}} file, stdio or remote. Imported servers start disabled so you can review them, mark keys as secret, then enable.

        Open Browse, search the MCP Registry or Glama, filter by npm, PyPI, OCI or remote, pick a version, fill in the keys it asks for, and install. Every install shows you the launch spec before it runs anything.

      4. 4

        Bundle them and lock them down

        Require bearer tokens by default, make a group so one URL carries several servers, then mint a token that opens only that group.

        # servers set to "inherit" (the default) now require a token
$ curl -X PATCH http://127.0.0.1:8080/api/settings \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' \
    -d '{"default_auth_provider": "bearer"}'

# every server, present and future, behind /g/team/mcp
$ curl -X PUT http://127.0.0.1:8080/api/groups/team \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' \
    -d '{"members": "*"}'

# a token for your laptop that opens that group and nothing else
$ curl -X POST http://127.0.0.1:8080/api/tokens \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' \
    -d '{"name": "laptop", "scope": "group:team"}'

        Pass a list of server ids instead of "*" to pick members by hand. Everything here is also in Settings.

      5. 5

        Add your people

        Create a member, choose whether they can run code on the box, and mint their login token. They paste it at the same login screen you use.

        $ curl -X POST http://127.0.0.1:8080/api/users \
    -H "Authorization: Bearer $T" -H 'content-type: application/json' \
    -d '{"name": "alice", "role": "member", "local_runners": false}'

# shown once: hand it to alice
$ curl -X POST http://127.0.0.1:8080/api/users/<id>/credentials \
    -H "Authorization: Bearer $T"

        Or use Settings → Users. Alice only ever sees the servers they create or that you assign to them.

      6. 6

        Connect your clients

        Streamable HTTP clients take the URL and a header directly:

        {
  "mcpServers": {
    "team": {
      "type": "http",
      "url": "https://mcp.example.com/g/team/mcp",
      "headers": { "Authorization": "Bearer mcpe_…" }

  }
}

        A client that can only launch a local command goes through mcp-remote:

        {
  "mcpServers": {
    "team": {
      "command": "npx",
      "args": ["-y", "mcp-remote",
        "https://mcp.example.com/g/team/mcp",
        "--header", "Authorization:${AUTH}"],
      "env": { "AUTH": "Bearer mcpe_…" }
    }
  }
}

      FAQ

      Fair questions.

      Does it sandbox servers from each other?

      No. Local runners run as the mcpelevator process user, and roles control who manages what, not what a process can touch. If you need more separation, use the Docker runner with its Docker-in-Docker sidecar, and only give the local-runner permission to people you'd trust with the machine.

      Which clients can connect?

      Anything that speaks Streamable HTTP connects directly. Stdio-only clients go through mcp-remote. claude.ai web and mobile connectors need OAuth, which you can provide with Cloudflare Access or your own authorization server.

      Do I need Docker?

      The Docker image is the easy path, since it carries every runtime. A source install works with Python, uv and Node on the host.

      What does it record about my calls?

      Hourly counts per server and per tool. Never the arguments or the results.

      Can I still run a server locally later?

      Yes. Any local server exports as an .mcpb bundle for Claude Desktop, built from the exact launch config the instance runs, with secrets turned into prompts.

      What does it cost?

      Nothing. It's MIT licensed and runs on hardware you already have.
